# ADR-012 — مرجع اجرایی و سیاست دادهٔ پذیرش S2

تاریخ: ۱۷ نوامبر ۲۰۲۶ · تصمیم معماری در اجرای دستور مستقیم مالک برای انجام و بستن فاز توسط مجری فعلی.

## تصمیم و حدود اختیار

مرحلهٔ S2، تحویل مهندسی وب/BFF، هویت، نقش و داده روی هستهٔ واحد Kotlin است. پذیرش آن به معنی آماده‌بودن تولید، مجوز ورود دادهٔ مشتری، فروش اشتراک، اتصال مدل هزینه‌زا یا انتشار برنامه در فروشگاه نیست. این مجوزها همچنان گیت مستقل دارند. هیچ امضا یا بازبینی انجام‌نشده‌ای به Chief یا صالحه نسبت داده نمی‌شود.

مالک اجرای مستقل پایان فاز را به همین مجری سپرده است. انتخاب‌های زیر تصمیم‌های اجرایی نسخه‌دار مجری‌اند؛ ادعای دریافت سند یا محیط خارجیِ ناموجود نیستند. آزمون و رسیدهای نهایی باید جداگانه روی SHA دقیق پذیرش شوند؛ این ADR به‌تنهایی فاز را نمی‌بندد.

## مرجع پنل

پنل پیاده‌شدهٔ **خود White Hat** در `apps/web-bff/public`، با adapter موجود `apps/web-bff/server.mjs` و visual assets محفوظ alpha، مرجع اجرایی S2 انتخاب می‌شود. source commit: `30bda6b2abd528439c1865c13329ed67915c387d`؛ شش فایل و SHA256 آن‌ها در `contracts/acceptance/s2-panel-source.json` قفل‌اند. کنترل مستقل hash و inventory در موتور کیفیت hard gate است.

این تصمیم «پنل Elyora» یا بازسازی UI جدید را وارد محصول نمی‌کند. وجود یا جدیدتربودن طراحی خارجیِ ارائه‌نشده ادعا نمی‌شود؛ اگر بعداً تحویل شد، به‌عنوان تغییر نسخه‌دار روی همین مرجع بررسی می‌شود. source pin اکنون انتخاب صریح منبع پیاده‌شده است، نه ادعای کشف منبع مفقود.

## محیط پذیرش

محیط مرجع یک GitHub Actions runner ایزوله است: Keycloak نسخهٔ پین‌شده با digest ثبت‌شده، HTTPS با CA یک‌بارمصرف، verifier همان کد تولیدی Kotlin، PostgreSQL با نقش non-owner/NOBYPASSRLS، دو نمونهٔ BFF با store نشست مشترک رمزگذاری‌شده و مرورگر Chromium واقعی. `WH_DEV_INSECURE_HTTP` در این محیط فعال نیست. trust نامعتبر باید رد شود. Keycloak در این محیط نرم‌افزار واقعی IdP است؛ حساب‌ها و provider تحلیل مصنوعی‌اند.

دو نمونهٔ BFF authority مستقل کسب‌وکار ندارند؛ فقط transport احراز هویت را به اشتراک می‌گذارند. Kotlin تنها نویسندهٔ decision/run/permission/usage است. schema owner فقط bootstrap/migration آزمایش را انجام می‌دهد؛ حساب API superuser یا bypass-RLS نیست.

این **reference staging** هدف پذیرش مهندسی S2 است؛ جای استقرار مشتری با دامنه، IdP سازمانی، secrets manager و ظرفیت واقعی را نمی‌گیرد. image این آزمون، انتخاب نسخهٔ تولید یا ادعای جدیدترین/امن‌ترین نسخه نیست؛ قبل از استقرار باید نسخه و digest و vulnerability policy مستقل تعیین شوند.

## سیاست دادهٔ S2 reference، نسخهٔ ۱

| دسته | سیاست اجرایی محیط مرجع |
|---|---|
| حساب/هویت | فقط حساب ساختگی `example.test`؛ رمز تصادفی هر اجرا، فایل خصوصی موقت؛ هیچ credential مشتری مجاز نیست |
| تصمیم و run | فقط دادهٔ ساختگی؛ مالکیت و workspace در Kotlin؛ هیچ writer دوم و انتقال خودکار حساب/رمز alpha وجود ندارد |
| usage/receipt/مالی | فقط fixture با برچسب روشن؛ مجهول null؛ هیچ صورت‌حساب یا پرداخت واقعی فعال نیست |
| consent/training | بازخورد پیش‌فرض غیرفعال؛ فعال‌سازی workspace با مجوز سرور و opt-in کاربر؛ عدم جمع‌آوری سن/جنسیت/موقعیت و عدم آموزش از محتوای خصوصی |
| نشست | AES-GCM، TTL مطلق موجود، refresh و revoke؛ logout موفق باید row نشست را حذف کند؛ کلید و توکن به artifact نمی‌روند |
| log/evidence | فقط assertion، نسخه، شمارش و خطای redacted؛ بدون credential، session cookie، صوت یا متن مشتری؛ رسیدهای CI فعلاً ۷ روز، خلاصهٔ بدون راز در Git ماندگار |
| نگهداری/حذف | PostgreSQL و realm یک‌بارمصرف؛ shutdown و حذف volume/container و فایل/اعتماد موقت در پایان هر اجرا؛ logout هم جداگانه حذف نشست را اثبات می‌کند |
| دادهٔ قدیمی | انتقال فقط از snapshot ساختگی read-only با نگاشت one-to-one؛ unmapped/ambiguous قرنطینه/رد، نه اتصال حدسی؛ رمز و نشست منتقل نمی‌شوند |
| backup/rollback | دو cluster مستقل، snapshot قبل از cutover و آزمون حفظ write جدید؛ RPO صفر نسبت به writeهای checkpoint fixture و سقف زمانی کل rehearsal برابر ۱۲۰ ثانیه؛ این ظرفیت یا RPO/RTO تولید نیست |

دادهٔ مشتری تا تعیین retention/deletion واقعی، مبنای رضایت، قواعد مالی/audit، نگهداری backup، encryption/KMS، RPO/RTO تحت بار و محیط مصوب وارد نمی‌شود. این محدودیت باید در بستهٔ تحویل و تصمیم انتشار باقی بماند؛ نه با فلگ پنهان یا دادهٔ نمایشی دور زده شود.

## معیار پذیرش و گیت‌های باقی‌مانده

S2 فقط وقتی پذیرفته می‌شود که source-pin، قرارداد معماری، موتور کیفیت و suites موجود، آزمون Keycloak/TLS/refresh/failover/نقش DB و axe/ARIA/keyboard، rehearsal بازیابی و حذف محیط واقعاً روی همان SHA موفق باشند. automationِ accessibility به معنی داوری انسانی screen-reader نیست؛ آزمون انسانی assistive technology برای ورود به تولید باز می‌ماند و باید صریح گزارش شود.

پذیرش تولید/مشتری، مدل واقعی و داور انسانی، صوت، native install/signing و billing مستقل‌اند. هیچ‌یک با بسته‌شدن مهندسی S2 پذیرفته اعلام نمی‌شوند. اگر آزمون یا شاهد این فاز FAIL/UNKNOWN باشد، گزارش closure صادر نمی‌شود.

## بازگشت

مرجع قبل از این تصمیم `053d284c058f582ae4ff1a805272fac09edc3987` و کد آزموده‌شدهٔ قبلی `cc101d00dbd63df0a4e7586e01a6c9413d953e71` محفوظ‌اند. تغییر verifier استخراج همان منطق قبلی برای reuse در آزمون واقعی است؛ داده یا migration جدید ندارد. پیش از write مشتری، revert کنترل‌شده ممکن است؛ پس از write واقعی، قواعد ADR-010 و حفظ writeهای مقصد همچنان لازم‌اند.
