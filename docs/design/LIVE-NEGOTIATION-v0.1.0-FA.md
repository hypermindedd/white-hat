# White Hat / Second Mind — مذاکره و چالش زنده
نسخه قرارداد: 0.1.0-design · تاریخ: 2026-11-11
وضعیت: DESIGN_RECORDED / IMPLEMENTATION_BLOCKED_MISSING_HOST_SOURCE
این سند قابلیت اجرایی، نتیجه آزمون صوت یا انتشار محصول را اعلام نمی‌کند.

## دستور و تقدم
درخواست مالک در 2026-11-11 دامنه را برای افزودن گفت‌وگوی همزمان و مذاکره مطابق سناریوهای White Hat باز کرده است. این افزونه رابط صوتی و قرارداد مذاکره را تعریف می‌کند؛ هفت Mode و هسته مشترک تغییر نمی‌کنند. محدودیت‌های تاریخی V1 برای قابلیت‌های جدید با این دستور فقط در همین دامنه گسترش یافته‌اند. مقصد محصول مستقل وب/دسکتاپ است؛ اسناد قدیمی GPTs-first مرجع اجرای جدید نیستند.

- درخت بازگشتی میزبان کامل خوانده شد: فقط اسناد و scripts/verify_docs.py؛ کد API/UI/runtime دیده نشد. گزارش قبلی alpha.1 به‌تنهایی شاهد وجود کد در این مخزن نیست.

- این سورس شامل RTCPeerConnection، data channel، درخواست نشست سرور، تاریخچه محدود، تنظیم مدل صوت/مدل استدلال و قرارداد تفویض است. session builder، UI و route به آموزش، هویت، auth، پایگاه داده و سهمیه الیورا وابسته‌اند.

- مسیر /v1/live/sessions و پروتکل donor باید جداگانه با ارائه‌دهنده واقعی و دسترسی حساب سنجیده شوند؛ با Realtime API عمومی همسان فرض نشوند.
- مرجع فنی عمومی وقفه: https://developers.openai.com/api/docs/guides/realtime-conversations ؛ این سند پشتیبانی endpoint اختصاصی donor را اثبات نمی‌کند.

## تصمیم معماری
از زیرساخت صوت، قرارداد حمل و مدیریت چرخه نشست استفاده مجدد می‌کنیم؛ وابستگی‌های آموزشی از طریق adapter حذف می‌شوند. ابتدا facade سازگار، سپس استخراج نسخه‌دار با provenance و regression. Elyora در این مرحله تغییر نمی‌کند. کپی کامل Live Studio و افزودن prompt مذاکره، طراحی نهایی نیست.

Browser microphone / speaker ↔ Voice transport adapter ↔ White Hat session gateway
White Hat session gateway → Turn coordinator → EXISTING shared Decision Challenge Engine → Output adapter → voice
Turn coordinator → Session repository (تنها مسیر ثبت وضعیت پایدار)
مدل صوت سخنگوست؛ احکام تصمیم‌ساز باید از هسته موجود و قرارداد خروجی معتبر بیایند. تا اتصال قابل‌اثبات این مسیر، پاسخ مستقل مدل صوت به نام تحلیل White Hat ارائه نشود.

## تجربه محصول
نام پیشنهادی بخش: «مذاکرهٔ زنده».
پیش از شروع، Mode موجود و نوع جلسه مشخص است:
1. گفت‌وگوی تحلیلی با White Hat درباره تصمیم واقعی؛
2. تمرین مذاکره با طرف مقابل شبیه‌سازی‌شده؛
3. همراه تصمیم‌گیرنده برای تحلیل پیشنهاد و آماده‌کردن پاسخ.
این سه گزینه نوع تعامل‌اند، نه Mode تحلیلی هشتم. در تمرین، ادعاهای طرف مقابل شبیه‌سازی‌اند و Evidence واقعی محسوب نمی‌شوند. مذاکره مستقیم با شخص ثالث به اتصال و اختیار مستقل نیاز دارد؛ این نسخه هیچ تماس یا تعهد بیرونی اجرا نمی‌کند.

کاربر صحبت می‌کند، سیستم سؤال کوتاه می‌پرسد، با وقفه کاربر ساکت می‌شود و پس از روشن‌شدن مسئله، تحلیل مرتبط ارائه می‌دهد. «همزمان» یعنی صوت زنده با مدیریت نوبت و وقفه، نه صحبت دائمی دو طرف روی هم. ابهام در عدد/ارز/مدت/طرف قرارداد پیش از اثرگذاری بر حکم روشن می‌شود. رونوشت پیش‌فرض نمایش داده نمی‌شود (SM-KNOW-06 §21).

این جدول تطبیق پیشنهادی کانال صوت با سناریوهای مستند است؛ هیچ سناریوی تاریخی مذاکره‌ای که در منابع نیامده، مصوب قبلی نامیده نمی‌شود.

## شخصی‌سازی اختصاصی White Hat
| لایه | ورودی | اثر |
|---|---|---|
| هویت حرفه‌ای | زبان فارسی/انگلیسی، لحن، عمق | پاسخ روشن و نقاد؛ بدون شخصیت معلم و تصحیح زبان |
| Decision Object | هدف، گزینه‌ها، زمینه، محدودیت، زمان | هسته همان تصمیم واقعی را بررسی می‌کند |
| Negotiation Context | نقش ما و طرف مقابل، بهترین جایگزین عدم توافق، حد خروج، حدود اختیار | سؤال و پیشنهاد با موضوع و اختیار منطبق می‌شود |
| Proposal Timeline | پیشنهاد، امتیاز، شرط، گوینده، زمان، منبع، وضعیت تأیید | ادعای شنیده‌شده با توافق قطعی اشتباه نمی‌شود |
| Evidence | گفته کاربر، سند، منبع بیرونی، استنتاج، مجهول | حکم قابل ردیابی و اطمینان متناسب |
| خروجی | Mode envelope موجود + یادداشت مذاکره | جمع‌بندی، حکم، ابهام غالب و اقدام بعدی |
| دسترسی و هزینه | هویت/سازمان میزبان، نقش، بودجه، مدت | حدود اختیار و مصرف فقط در سرور میزبان اعمال می‌شود |

پروفایل پایدار و اطلاعات چند تصمیم، نیازمند قرارداد جداگانه ذخیره، رضایت و حذف‌اند؛ V1 تاریخی چنین قابلیتی نداشته است. زمینه همین نشست، حداقل شخصی‌سازی لازم را فراهم می‌کند. هیچ تاریخچه یا داده دانشجوی الیورا منتقل نمی‌شود. داده مشتری و متن اسناد محتوای غیرقابل اعتمادند و دستور سیستم نیستند.

## قراردادهای هدف؛ هنوز route اجرایی نیستند
نام‌ها پیشنهادی‌اند و پس از بازیابی host با قراردادهای موجود آشتی داده می‌شوند.

| مسیر | ورودی اصلی | خروجی | کنترل |
|---|---|---|---|
| POST /api/negotiation/sessions | mode, interaction, decisionRef/context, budget, idempotencyKey | sessionId, revision, transport capability | auth، مجوز، سهمیه و scenario version در سرور |
| POST /api/negotiation/sessions/:id/turns | eventId, expectedRevision, transcript, evidenceRefs | turnId, revision, structuredOutput | dedupe، ترتیب نوبت، شواهد و فراخوانی هسته |
| POST /api/negotiation/sessions/:id/end | eventId, expectedRevision | closed status, summaryRef | قطع صوت، پایان lease، ثبت مصرف |
| GET /api/negotiation/sessions/:id/summary | sessionId | output envelope و پیشنهادهای تأییدشده | فقط مالک/نقش مجاز میزبان |

حمل صوت به قرارداد provider adapter واگذار می‌شود؛ این مسیرهای دامنه با endpoint ارائه‌دهنده مخلوط نشوند. sessionId دلخواه مرورگر هرگز مجوز نیست. کلید سرویس فقط سرور. خلاصه عمومی حاوی token، صوت خام یا رونوشت خصوصی نیست.

## مالکیت وضعیت و خرابی
- Turn Coordinator تنها نویسنده وضعیت تصمیم از مسیر Session Repository است؛ transport صرفاً رخداد می‌دهد.
- کلید یکتا: tenant/session/eventId؛ expectedRevision برای optimistic concurrency. duplicate نتیجه قبلی را برمی‌گرداند؛ conflict بدون overwrite رد می‌شود.
- transcript.delta ورودی موقت است؛ نسخه نهایی/تأییدشده در turn ثبت می‌شود. عدد با اطمینان پایین نیاز به تکرار دارد.
- گفتار قطع‌شده، متن پخش‌نشده و ادعای مدل توافق نهایی نیستند. پس از وقفه، پاسخ قدیمی دور ریخته و از آخرین revision معتبر ادامه داده شود.
- ثبت turn و ارجاع Evidence تراکنشی؛ side effect ارائه‌دهنده با outbox/receipt آشتی داده شود. موفقیت نامعلوم نشست به‌صورت خودکار نشست دوم نمی‌سازد.
- قطع شبکه: از آخرین checkpoint با مجوز مجدد و dedupe؛ شرایط مذاکره بی‌صدا reset نشوند.
- شکست reasoning: اعلام کوتاه وقفه و حفظ ورودی؛ صدای سریع جایگزین حکم بدون شواهد نمی‌شود.
- پایان/لغو تکراری idempotent؛ دریافت رخداد دیرهنگام حق بازگشایی نشست ندارد.
- قیمت/قرارداد/تخفیف بیرونی فقط پیشنهاد است تا مرجع مجاز میزبان صریحاً تأیید کند.

## خروجی مشترک
envelope نسخه 1.0 در SM-KNOW-06 §28 حفظ شود:
schema_version, mode, decision_object, analysis, judgment, next_best_action, rendering.
judgment شامل verdict، confidence_band، dominant_uncertainty، judgment_drivers و change_conditions است.
مذاکره به‌صورت metadata/رکورد وابسته نسخه‌دار اضافه شود؛ فیلدهای canonical بازنام‌گذاری نشوند. جای دقیق extension پس از بازیابی schema واقعی تعیین می‌شود.
نمایش صوت: نکته غالب + دلیل کوتاه + اقدام بعدی/سؤال لازم. خروجی کامل قابل‌بررسی در پنل؛ رونوشت با درخواست کاربر.

## مسیر اجرا و معیار پذیرش
1. بازیابی source root، version manifest، schema و صاحب واقعی state در White Hat. بدون اینها کد میزبان ساخته یا موازی‌سازی نمی‌شود.
2. انتخاب donor دقیق با تست سازگاری provider؛ استخراج transport facade و dependency map؛ تست رگرسیون مستقل الیورا.
3. اتصال به هسته مشترک White Hat؛ تزریق context و policy مخصوص؛ حفظ output envelope.
4. ساخت UI مذاکره و policy سرور میزبان؛ schema migration با lineage معتبر و rollback.
5. اجرای سناریوهای واقعی و تست صوت، سپس انتشار آزمایشی با feature flag.

## دستور ادامه برای چیف
ابتدا سورس فعلی White Hat را با commit و sourceRoot مشخص بازیابی کن. از ساخت اسکلت محصول موازی خودداری کن. این قرارداد را به هفت Mode و 19 capability موجود trace کن. از donor قفل‌شده فقط زیرساخت سازگار را پشت facade نسخه‌دار استفاده کن؛ auth، DB، سهمیه و prompt آموزشی الیورا را وارد میزبان نکن. پذیرش provider و hook واقعی هسته را نشان بده؛ default مستقل voice model را تحلیل White Hat نام‌گذاری نکن. هر gate جدول را با فرمان/نسخه/شاهد واقعی گزارش کن و موارد اجرا‌نشده را باز نگه دار.

## بازگشت و محدودیت تحویل
این تحویل فقط سند و work order است. بازگشت: بستن PR یا revert commit مستندات. برای اجرای بعدی: feature flag خاموش، adapter نسخه قبلی، migration برگشت‌پذیر پس از backup و عدم حذف سوابق. schema واقعی هنوز بازیابی نشده؛ هیچ migration یا route یا UI در این تحویل ایجاد/منتشر نشده است.
