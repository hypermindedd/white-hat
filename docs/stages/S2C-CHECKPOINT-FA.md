## C1 — عملیات و مجوز

| عملیات | مرجع مجوز |
|---|---|
| فهرست و تغییر عضویت، فعال یا غیرفعال‌سازی | OWNER همان workspace |
| اعطا یا لغو مجوز پیگیری | OWNER برای عضو فعال SUPPORT همان workspace |
| صف پیگیری و ثبت disposition | OWNER یا SUPPORT با مجوز صریح |
| مشاهدهٔ متن و نتایج تصمیم‌ها و اجراها | صاحب منبع با نقش مجاز در همان workspace |
| مصرف تجمیعی | OWNER و ADMIN همان workspace |

صف پشتیبانی فقط شناسهٔ اجرا و disposition را می‌دهد. ثبت پیگیری در audit می‌آید و مبلغ، شمارندهٔ مصرف، وضعیت run، یا اجازهٔ retry را تغییر نمی‌دهد. غیرفعال‌سازی یا تبدیل نقش SUPPORT مجوز پیگیری را پاک می‌کند. مسیر کاربر، سابقهٔ اجرا و پنل پشتیبانی از هم جدا شده‌اند. این برش یک مجوز قابل اعطا دارد. نقش‌های سفارشی چندمجوزه، پنل مالی/هزینه، داشبورد latency و خطا، feature flags و صف feedback/quality هنوز پیاده نشده‌اند.

## C2 — نشست، داده و rollback

BFF از PostgreSQL اختصاصی نشست و کلید ۳۲بایتی Base64 استفاده می‌کند. SQL در `apps/web-bff/db/session-store.sql` با حساب schema owner اعمال می‌شود. نقش BFF فقط عملیات داده روی دو جدول نشست و جریان ورود دریافت می‌کند. کلید اول برای رمزگذاری و کلیدهای قدیمی برای خواندن بازهٔ چرخش‌اند. همهٔ replicaها هم‌زمان مجموعه کلید سازگار دریافت می‌کنند. کلیدهای نشست از secret manager تأمین می‌شوند. پس از تخلیهٔ نشست‌های قدیمی و خارج‌شدن از بازهٔ بازگشت، کلید قدیمی حذف می‌شود. نشست و callback میان replicaها مشترک‌اند. قفل ردیفی، refresh هم‌زمان را سریالی می‌کند. دسترسی بدون دادهٔ معتبر fail closed است. سقف موجود flow و quota تحلیل حفظ شده‌اند. آزمون بار، تنظیم throttling در ingress، مدیریت چرخهٔ رضایت و تست failover IdP هنوز بازند.

Kotlin با حساب non-owner و NOBYPASSRLS اجرا می‌شود. RLS روی هفت جدول scopeدار دفاع در عمق دارد و متن خصوصی همچنان با مالکیت در برنامه محدود می‌شود. اتصال worker برای claim و recovery مورداعتماد است و context کاربردی آن در تراکنش فعال می‌شود. محدودیت بر پایهٔ context تراکنش، تضمین برای credential افشاشدهٔ حساب برنامه ایجاد نمی‌کند. workspaces و memberships به‌عنوان رجیستری عضویت با کنترل برنامه اداره می‌شوند. پیش از محیط واقعی، حساب‌های اجرا، مهاجرت، پایش و نشست جداگانه provision و بازبینی شوند.

تمرین انتقال روی کپی SQLite مصنوعی و پایگاه PostgreSQL آزمایشی انجام می‌شود. برای cutover واقعی، نگاشت شناسه به subject تأییدشده، نسخهٔ پشتیبان و بررسی موارد ناقص لازم است. بعد از اولین write در مقصد، برگشت مستلزم توقف ورود داده، backup و replay یا forward fix آزموده‌شده است. برگشت کد به نسخهٔ پیش از V3 به‌تنهایی مسیر rollback داده نیست. تا پیش از cutover، مسیر عملیاتی روی منبع قبلی می‌ماند و checkpoint مقصد مستقل است.

## به‌روزرسانی بازبینی C

این بخش وضعیت اجرایی بالا را به‌روز می‌کند. سه مجوز مستقل `REVIEW_RUN_INCIDENTS`، `READ_RUN_METRICS` و `REVIEW_QUALITY_FEEDBACK` برای نقش SUPPORT قابل اعطا هستند. مالک می‌تواند دریافت بازخورد داوطلبانه را فعال کند. کاربر می‌تواند امتیاز ۱ تا ۵ را پس بگیرد. صف پشتیبانی امتیاز و شناسهٔ اجرا را نمایش می‌دهد و متن تصمیم را در بر نمی‌گیرد. گزارش ۳۰روزه شمار اجراهای ناموفق یا نامطمئن و P95 زمان ثبت تا پایان را نشان می‌دهد. هزینهٔ دلار از مبلغ مستند و ثبت دستی مالک محاسبه می‌شود. گزارش، تعداد اجراهای پوشش‌داده‌شده توسط رسید و جمع ثبت‌شده را نمایش می‌دهد. اتصال صورتحساب ارائه‌دهنده هنوز باز است.

SQL نشست اکنون سه جدول دارد. هر سه جدول باید پیش از rollout ایجاد شوند. محدودیت پایدار میان replicaها، ۱۸۰ درخواست API برای هر subject و ۴۰ شروع login برای هر peer در دقیقه است. پنجره بر ساعت همگام میزبان‌ها تکیه دارد. پشت reverse proxy، peer می‌تواند همان proxy باشد. تنظیم IP در ingress و آزمون ظرفیت واقعی بخشی از rollout است. حفظ نشست، RLS و بازیابی پس از ثبت یک تغییر مصنوعی روی مقصد آزمایش شده‌اند. بازیابی به‌صورت forward restore از snapshot بعد از write و با توقف مصنوعی نویسنده انجام شد. cutover واقعی، inverse migration به SQLite، lifecycle جامع consent/retention و آزمون failover باز هستند.

اسکریپت `evaluation/score_s3.py` قواعد عددی و شکست بحرانی را روی امتیازهای انسانی اعمال می‌کند. آزمون مصنوعی اسکریپت معادل شواهد کیفیت مدل نیست. هنوز مدل عملیاتی با مجوز و سقف، داوری مستقل، fixtureهای تکمیلی و نمایهٔ حالت‌ها لازم است. سورس commit صوت در هر دو اتصال GitHub در آزمون دسترسی ۴۰۴ داد. وضعیت پذیرش S2 و بند C باز می‌ماند.
