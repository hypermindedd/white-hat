# White Hat | قرارداد ورود و رفتار کلاینت C5

مبنا [راهنمای PR #2، بند C5](https://github.com/hypermindedd/white-hat/blob/9c291e0d65d5dbbf29d8bdffaf8c74f345e279d7/docs/handoffs/SALEHE-ONBOARDING-EXECUTION-2026-11-14-FA.md) و [ADR-010](../architecture/ADR-010-KOTLIN-PLATFORMS-FA.md) است. API موجود در `contracts/openapi/openapi.json` مبنای این نسخه است.

## ورود بومی

هر اپ به‌عنوان public client از OIDC Authorization Code + PKCE S256 در مرورگر سیستم استفاده می‌کند. آداپتور بومی باید issuer، ID Token و nonce، تطبیق state و redirect دقیق را کنترل کند. ورود با نشست وب BFF جریان جداگانه‌ای دارد. برای هر پلتفرم شناسهٔ کلاینت و redirect مجاز در IdP تنظیم می‌شود. کلاینت بومی با secret تعبیه‌شده توزیع نمی‌شود. RS256، issuer و audience تنظیم‌شدهٔ API، `sub` معتبر، `exp` و `token_use=access` برای access token لازم‌اند. نقش workspace از پایگاه‌دادهٔ Ktor خوانده می‌شود.

| پلتفرم | مسیر پیشنهادی ثبت redirect | ذخیره و آزمون پذیرش |
|---|---|---|
| Android | App Link تأییدشده در صورت پشتیبانی IdP | ذخیره مبتنی بر Keystore، callback و resume، APK/AAB امضاشده، نصب و ارتقا |
| iOS | Universal Link در صورت پشتیبانی IdP و نشست ورود سیستم | Keychain، آزمون callback روی iPhone/iPad، امضا و نصب/ارتقا |
| macOS | loopback با IP و درگاه موقت در صورت پشتیبانی IdP | Keychain، callback و بازگشت به اپ، signing و notarization و نصب/ارتقا |
| Windows | loopback با IP و درگاه موقت در صورت پشتیبانی IdP | ذخیرهٔ امن سیستم، callback، signing و نصب/ارتقا |

[OAuth 2.0 for Native Apps، RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)

مالک محیط باید IdP هدف، issuer، metadata/JWKS، API audience، client IDهای عمومی، redirectهای مجاز و سیاست expiry/rotation/revocation را ثبت کند. نمونهٔ آزمایشی این تحویل یک JWT کوتاه‌عمر RS256 است که داخل fixture با audience `whitehat-api` و `token_use=access` ساخته می‌شود. کلید و JWT fixture وارد بستهٔ تحویل نمی‌شوند. شاهد IdP هدف به توکن کوتاه‌عمر همان محیط، login/refresh/logout و تأیید fail-closed برای issuer/audience/expiry/نوع توکن نیاز دارد.

## بازیابی و وضعیت اجرا

| پاسخ | قرارداد کلاینت |
|---|---|
| 401 | refresh موازی یک session ادغام می‌شود. GET فقط یک‌بار با توکن تازه و همان حساب تکرار می‌شود. پس از refresh موفقِ درخواست تغییردهنده، خطا با امکان تکرار صریح به فراخواننده برمی‌گردد. با نشست غیرقابل تمدید یا توکن تازهٔ دوباره ردشده، ورود لازم است. |
| 409 / revision | آخرین نسخهٔ تصمیم خوانده شود و حل تعارض به کاربر سپرده شود. |
| 409 / idempotency یا اجرای فعال | قصد اولیه و شناسهٔ اجرا بررسی شوند. برای enqueue مبهم همان key و revision حفظ شوند. |
| 409 / pause یا provider | وضعیت توقف یا سرویس به‌صورت متمایز گزارش شود. |
| 429 / سهمیه روزانه | با کد `DAILY_LIMIT_REACHED` سهمیهٔ روز UTC نمایش داده شود. زمان انتظار فرض نشود. |
| 429 / نرخ درخواست | هدر `Retry-After` در صورت وجود به لایهٔ نمایش منتقل می‌شود. |
| polling و لغو | روی run ID موجود ادامه دهید. `cancellation_requested` فعال است. با وضعیت نهایی و `reconciliation_required` جریان متوقف می‌شود. در وضعیت نامطمئن، ایجاد اجرای خودکار انجام نمی‌شود. |

پوشش این نسخه شامل پروفایل/عضویت، ایجاد workspace، هفت Mode، فهرست/ثبت/خواندن/ویرایش تصمیم و شروع/پیگیری/تاریخچه/لغو تحلیل است. فهرست‌های فعلی سقف ۱۰۰ دارند. حذف تصمیم و pagination نیازمند قرارداد محصول‌اند. خروجی `legacy-alpha.1` برای لایهٔ نمایش به‌صورت JSON باقی می‌ماند. revision و توکن‌های مصرفی به‌شکل ۶۴بیتی و مصرف نامعلوم با null حفظ می‌شوند.

## معیار بسته‌شدن

تثبیت تنظیمات IdP هدف، پیاده‌سازی آداپتور ورود و ذخیرهٔ امن برای هر اپ، آزمون کارکرد روی دستگاه واقعی و نصب/ارتقا/امضای چهار پلتفرم برای پذیرش نهایی C5 لازم‌اند. کنترل TLS استقرار و ثبت نتیجهٔ CI و بازبینی مستقل بر عهدهٔ مرحلهٔ تحویل است.

## شواهد آماده‌سازی پذیرش

جریان مشترک تعویض کد، refresh و revoke پیاده شده است. JVM helper برای تولید verifier، اعتبارسنجی امضای RS256 با JWKS و callback محلی دسکتاپ آماده است. آزمون یکپارچه با HTTPS و IdP آزمایشی، callback نامعتبر، صدور توکن، rotation، revoke و چرخهٔ API را پوشش می‌دهد. اجرای مرورگر سیستم در آزمون با یک رانندهٔ HTTP جایگزین شده است.

برای پذیرش روی مقصد، مالک محیط باید دامنهٔ HTTPS آزمون، مشخصات ثبت چهار کلاینت در IdP، میزبان‌ها و دستگاه‌های پذیرش و دسترسی توزیع آزمایشی را ارائه کند. پس از اتصال آداپتورهای سیستم‌عامل و ساخت اپ‌های قابل نصب، روی هر پلتفرم نتیجهٔ login، لغو و timeout ورود، قطع شبکه، refresh/revoke، نصب پاک، ارتقا از نسخهٔ قبلی و اعتبار امضا ثبت شود. گیت CI در شاخهٔ پیشنهادی تعریف شده و اجرای راه‌دور باید پس از انتشار شاخه توسط مالک ثبت شود.
