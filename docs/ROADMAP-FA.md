# نقشه اجرای بعدی
ترتیب اجرایی پیشنهادی؛ تخمین مدت پس از تعیین ظرفیت تیم و آماده‌بودن Runtime ثبت می‌شود.

| فاز | خروجی | گیت خروج | نقش مسئول پیشنهادی |
|---|---|---|---|
| ۰ منابع | ۱۷ سند، رجیستری، راهنما و چشم‌انداز | کنترل صحت انتقال | معمار سیستم |
| ۱ مبنای RC0 | حل تعارض و ماتریس ردیابی نیاز→قاعده→تست | مرجع هر رفتار روشن | معمار محصول |
| ۲ بسته GPT | دستور مناسب نصب، ۷ فایل، تنظیمات و راهنمای نصب | smoke هفت Mode روی Runtime واقعی | سازنده فنی |
| ۳ آزمایشگاه | ≥۶۰ کیس کامل و fixture؛ تقسیم development/regression/holdout | انتظار هر کیس مستقل و روشن | مسئول ارزیابی |
| ۴ آزمون | خروجی خام، scorecard، failure، علت ریشه‌ای | معیارهای STATUS پاس | مسئول ارزیابی + بازبین انسانی |
| ۵ رگرسیون/انتشار | نسخه ثابت، known defects، شواهد، GO/NO-GO | SM-REL-001 | مسئول انتشار |
| ۶ پایلوت | کاربران واقعی، تصمیم بعدی، فایده و تمایل پرداخت | ارزش تکرارشونده | مسئول محصول |
| ۷ محصول مستقل | backend، schema، رابط، کنترل مصرف و مشاهده‌پذیری | برابری رفتار و آمادگی عملیاتی | تیم ساخت |
| ۸ تجاری‌سازی | بسته‌ها، قیمت، پشتیبانی و اقتصاد واحد | تقاضا و حاشیه اقتصادی | مسئول کسب‌وکار |

نام افراد و مسئولیت واقعی هنوز تعیین نشده‌اند. نقش‌های جدول پیشنهاد تخصیص‌اند.

## کارهای فوری

1. رفع موارد G01 تا G05 در [رجیستر فاصله‌ها](GAPS-FA.md).
2. آماده‌کردن نسخه نصب‌شدنی از Master Instructions با حفظ invariants.
3. استخراج Knowledge Runtime فقط از ۰۱ تا ۰۷.
4. تکمیل کیس‌های smoke هفت حالت و آزمون اصلاح داده/تغییر Mode.
5. اجرای نسخه مشخص، ثبت output دست‌نخورده، امتیازدهی و اصلاح علت ریشه‌ای.

رابط وب، پرداخت و دیتابیس گسترده پس از اثبات هوشمندی در اولویت قرار می‌گیرند. جزئیات آینده نباید دامنه V1 را بی‌صدا گسترش دهند.
